# Step 5: Per-symptom gotcha table

> Part of the `slopstopper-triage` skill. `SKILL.md` says when to read this; it is not loaded until then.

## Step 5: Per-symptom gotcha table

Common failures, with diagnostic step and the file the fix lives in. Categories use the Step 4 vocabulary: `code` / `suppress` / `tune`.

| Symptom | Diagnostic step | Cause | Fix location | Category |
|---|---|---|---|---|
| `Node.js vXX is not supported by Astro!` on `npm run build` across every reliability/Playwright workflow | Check `package.json` `engines.node` vs the `node` pin in `mise.toml` (`[tools] node`) | Workflows get node from the `mise.toml` pin via `jdx/mise-action`; the pin is older than the build needs | `mise use node@22` (or your version), commit `mise.toml`, since mise locally and CI read the same pin | config |
| `task ss:hygiene:complexity` errors with compression-tool usage text instead of cyclomatic output | `which lizard` returns a Homebrew `lz4-lizard` path | PATH collision: `lz4-lizard` compression utility shadows the Python `lizard` | `pip install --upgrade lizard`; reorder PATH so the Python `lizard` wins, or invoke `python3 -m lizard` | code (environment) |
| `task ss:security:secrets` flags an example connection string, sample API key, or emulator config | Open the flagged file: is it real credential or tutorial sample? | gitleaks regex matches sample content as a generic API key | Real → revoke + scrub history (code). Sample → path-scoped allowlist in `.gitleaks.toml` with `# why` | code OR suppress |
| `task ss:hygiene:docs-accuracy` flags backtick-quoted filenames that don't resolve | `git ls-files \| grep <name>`. The check already accepts a name any tracked or untracked-not-ignored file has, or a path any file's path ends with, so a flag means no such file exists (or it is gitignored) | Old docs reference renamed/moved files, or name a file that only exists in the reader's tree (a tutorial) | Fix the reference to the file's current name; for tutorial prose naming the reader's files, phrase it as an example ("for example, `x.py`") so the suggestion context skips it | code (docs) |
| `hygiene:docs-accuracy` reports "Broken Links Into This Repository" for an HTML page or a skill | Open the flagged file at the line; the link's `blob/main/<path>` names a path that isn't on disk | The file was renamed, moved into the CLI wheel, or deleted, and the page kept pointing at it. This is `hygiene.docs_accuracy.extra_paths` doing its job, since these files are outside `docs/` and were never scanned before | Fix the link (or the prose around it, since often the whole excerpt describes something that no longer exists). Don't remove the path from `extra_paths` to silence it | docs |
| `hygiene:docs-structure` reports `Unrouted doc: docs/<path>.md` | Read the message. It says whether the doc is linked *softly* (no trigger or "read"), routed from a README that is itself unreachable, or not linked at all; `.ss/reports/docs/docs-structure-report.md` lists every reachable doc with its hop count | A doc is reachable only through an explicit route, meaning a trigger-first "read" line (or a row of a "When you are… \| Do this" table) in `AGENTS.md`, `docs/README.md` or a README above it. A `## Contents` bullet or "see also" is a soft link agents skip | Add the row to the README the message names (`Before you <do X>, read <doc> for <what it holds>`), route the unreachable README first if that is the cause, or delete the doc if it is dead | docs |
| Any Snyk check (`sast`, `dependencies`, `iac`, `sbom`) exits `2` with `missing SNYK_TOKEN` / `could not authenticate` / `Authentication failed` | `slopstopper doctor` (the `snyk` row), then in CI: Settings → Secrets → is `SNYK_TOKEN` there and scoped to this repo? Locally: `echo ${SNYK_TOKEN:+set}` | The token is absent, or it belongs to a different Snyk tenant (an EU/AU token against the default US API reads as "invalid"), or it was revoked. The check refuses to pass a scan that never ran | Add the `SNYK_TOKEN` repository (or org-level) secret with a service-account token; for a regional tenant set the `SNYK_API` variable (`https://api.eu.snyk.io`); rotate per `docs/security/SNYK.md`. All four Snyk checks go green together once it exists | config (environment) |
| `security:sast` exits `2` with `Snyk Code is not enabled` (or `snyk code test` reports the org has no Snyk Code) | Open the Snyk org → Settings → Snyk Code | Snyk Code is switched off for the organisation `SNYK_ORG` names (it is off by default on a new org). Only SAST needs it; the other three Snyk checks run | Enable Snyk Code on that org (an org admin action), or point `SNYK_ORG` at an org that has it. Until then, either accept the red `sast` job or disable `ss-security-sast-check.yml` under `workflows.disabled` with a `# why` and say so | repo-admin (Snyk) |
| A Snyk check exits `2` with `org … not found` / `Unauthorized` for a valid token, or scans the wrong projects | `snyk config get org`; compare `SNYK_ORG` (repo variable) and `security.snyk.org` with the org's **slug** in its settings URL | `SNYK_ORG` holds the org's display name or group name instead of its slug, or names an org the service account isn't a member of. The variable wins over the yml key, so a stale variable silently overrides a correct config | Set `SNYK_ORG` to the slug (or remove the variable and set `security.snyk.org`); add the service account to that org | config |
| Every Snyk check exits `2` on a self-hosted or locked-down runner but passes on a hosted one, with a network error or a hang until the job timeout | Read the stderr block; try `curl -sI https://api.snyk.io` (or the regional host) from the runner | Egress allowlist: the runner can't reach `api.snyk.io` (or the regional API), `downloads.snyk.io` / `static.snyk.io` (the CLI binary the npm wrapper fetches on first run; the IaC rules) or `registry.npmjs.org` (the `snyk` package mise installs) | Allow the hosts in the table in `docs/security/SNYK.md` → "Egress allowlist", or bake the CLI into the runner image | Infra |
| `security:sast` fails on a finding ranked medium (SARIF `warning`) and you only want high to block | Read the report's severity column | `security.sast.fail_on` is set to `medium` (or `low`) in `.slopstopper.yml`. The default is `high`; below that severity findings are reported, not enforced | Set `security.sast.fail_on: high`, or leave it and fix (or `.snyk`-ignore) the finding if the repo chose the stricter line deliberately | config |
| `security:sast` fails on a finding that is a false positive (a test fixture, a sanitised path) | Read the report's issue id and file; the Snyk UI shows the dataflow | Snyk Code's analysis doesn't see the guard, or the file is test data | Add an `ignore` in `.snyk` keyed on the issue id, scoped to the path, with `reason:` and `expires:`. Never lower `fail_on` for one finding | suppress |
| `security:dependencies` fails on a vulnerability with no fixed version available | Read the report's fix column (`No fix available`) and the dependency path | Transitive dependency, upstream has not shipped a fix; the finding is real but not actionable today | `.snyk` ignore keyed on the Snyk issue id and the dependency path, with a `reason:` naming the upstream issue and an `expires:` a few weeks out so it is re-checked; or replace the dependency | suppress OR code |
| `security:dependencies` fails on a **licence** issue, not a CVE (`Licence issue: GPL-3.0 …`) | Read the report: the issue type is a licence policy breach and the severity is the one the org's policy assigns | The Snyk organisation has a licence policy and a (new) dependency breaches it. Real policy hit, gated like a vulnerability | Swap to a permissively-licensed alternative, or if the licence is acceptable for this project ask a Snyk org admin to adjust the licence policy (it is org-wide, not in this repo), or `.snyk`-ignore with a reason and expiry | code OR repo-admin (Snyk) |
| `security:dependencies` passes locally but fails in CI (or the reverse) on the same commit | `snyk --version` both sides (must match the `mise.toml` pin), then compare `SNYK_ORG` and `security.dependencies.include_dev` on both sides, and `git status` the lock file | Same pinned CLI and the same hosted database, so the difference is a different org (org-level ignores, licence policy), `include_dev` set on one side, an uncommitted lock file change, or an advisory published between the runs. See `docs/security/VULNERABILITY.md` → Local/CI Parity | Align the org and the knobs; re-run. Treat CI as the canonical verdict | environment |
| `security:dependencies` exits `2` with `Could not detect supported target files` or a manifest Snyk "could not resolve" | Read the stderr block: it names the manifest. `snyk test --all-projects --print-deps` reproduces it | A lock file out of date with its manifest, or an ecosystem that needs its build tool on the runner (Maven, Gradle, Go modules, Poetry) which the runner image lacks | Regenerate the lock file; install the build tool in the workflow before `ss-setup` (an extra step in your copy of the workflow is wiped on refresh, so prefer a runner image that has it) | code OR Infra |
| `security:iac` passes with `No IaC files found` on a repo that has Terraform / Kubernetes manifests | `snyk iac test --print-deps` or check the extensions; CloudFormation YAML must carry `AWSTemplateFormatVersion` or `Resources`, Kubernetes YAML must carry `apiVersion`/`kind` | Files Snyk doesn't recognise as IaC (templated Helm values, Terraform in an unusual extension, a directory the CLI skipped). The pass is honest: nothing was scanned | Rename or restructure so the CLI detects them; for Helm, scan the rendered manifests. If the repo genuinely has no IaC the note is the correct end state | code |
| `security:iac` fails on a rule that is wrong for this deployment (a public bucket that serves a static site by design) | Read the report's rule id (`SNYK-CC-…`) and resource path | Policy-as-code misfire for a deliberate choice | `.snyk` ignore keyed on the rule id, scoped to the resource path, with `reason:` and `expires:` | suppress |
| `security:sbom` exits `1` with `no supported manifest` | `ls` for a lock file or manifest; `snyk sbom --all-projects --format cyclonedx1.5+json` reproduces it | The repo has no dependency manifest Snyk resolves, so the SBOM would be empty. On a repo that ships software that is a compliance gap; on a docs repo or a pure-shell tool it is expected | Add the manifest / lock file, or set `security.sbom.allow_empty: true` with a `# why` for a repo with genuinely no dependencies | code OR tune |
| `security:sbom` exits `2` with `format … not accepted` | `snyk sbom --help` lists the formats | `security.sbom.format` names a format this CLI version doesn't support | Use one the pinned CLI lists (`cyclonedx1.5+json`, `cyclonedx1.6+json`, `spdx2.3+json` …), or move the `snyk` pin in `mise.toml` | config |
| `task ss:security:monitor` (the main-branch step) fails with a permissions error while `security:dependencies` passes | Read the step log: `snyk monitor` needs to create a project | The service account can test but not monitor: its role lacks project-create on the org | Give the service account a role with *monitor* permission (Org Admin, or a custom role), or accept that the project stays off the dashboard | repo-admin (Snyk) |
| `task ss:security:secrets` exits `2` with `gitleaks: command not found` | `which gitleaks`; `mise ls` | gitleaks comes from the `mise.toml` pin, and mise isn't installed or activated in this shell | `mise install` then re-run (or `mise exec -- task ss:security:secrets`). CI gets it from `jdx/mise-action` reading the same pin | config (environment) |
| A check exits `2` and the workflow is red with no findings in the report | Read the check's stdout. It names what's missing | Exit 2 means the check could not run: tool not installed, `SNYK_TOKEN` missing or for another tenant, required input missing, a scanner that wrote no report or exited with an error, a browser that never launched, a crash in the check (a traceback is printed), or an argument it has no parser for (`slopstopper run hygiene:complexity -- --max-ccn 5` is exit 2; the knob is `hygiene.complexity.max_ccn` in `.slopstopper.yml`). Not a verdict about the repo, so no main-branch tracking issue is opened or closed for it | Fix the environment or the invocation. The nine config-only checks take no arguments at all | config |
| A check is missing from the PR's checks list entirely: no run, no red, no skip | `slopstopper doctor` (its `workflows` lines), or `gh workflow list --all` and look for `disabled_inactivity` | GitHub disables any workflow with a `schedule:` trigger once the repo has had no activity for 60 days. A disabled workflow runs on no trigger, pull requests included, and never fails, so the failure tracker can't see it, and the scheduled production runs have stopped too | `gh workflow enable <id>` for each one doctor lists (it prints the command), then push to re-run the PR. A repo that goes quiet for 60 days will hit it again | config |
| `task ss:hygiene:docs-structure` exits 2 with `docs/ directory not found` or `docs/README.md not found` | `ls docs/README.md docs/index.md` | No map. A `docs/index.md` means a pre-0.15 Map Pattern repo, and the map is a README now (the message says so) | `git mv docs/index.md docs/README.md` and rewrite its rows as routes (`slopstopper-install` Step 5 has the migration) OR, with no docs at all, delete the four docs-* workflows | code (docs) OR delete check |
| `hygiene:docs-structure` reports `<map> line N → <doc>: "…" is a soft route`, `Route too deep`, `Doc over budget`, or `Legacy map` | Read the row. Each names the file and the limit | The map links a doc without saying when to read it; a route runs more hops than `max_route_depth` (3); a topic doc is past `max_doc_lines` (300); a `docs/index.md` sits beside `docs/README.md` | Reword the map row as trigger → "read" → file; route the deep doc from the map directly or merge the README that only routes onward; split the long doc by concern and route each part; fold the legacy index into the map and delete it. Knobs exist (`hygiene.docs_structure.*`) but tune only for a deliberate decision. If the docs aren't agent docs at all (a course, tutorials), exclude them with `hygiene.docs.exclude` | docs OR tune |
| Every reliability check fails at once on a repo with no browser surface, where `npm run build` produces nothing to serve or the audit reports no HTML/`<title>`/sitemap | `slopstopper profile show`. Is the profile `ui` on a repo that's actually an API or a library? | Wrong project-shape profile. The nine browser-and-SEO checks (smoke, e2e, accessibility, cwv, seo, broken-links, llms-txt, robots-txt, sitemap) assume HTML and a served site; on an API they audit nothing and fail rather than no-op | Set `profile: api` (or `library`) in `.slopstopper.yml` and **re-run `install.sh`**, since the key drives the set and the installer moves the files. Confirm with `slopstopper profile detect`. Don't chase these individually: one wrong profile shows up as 9 red checks | config |
| A single reliability check fails on a repo that's otherwise the right shape (an API whose docs site *does* want `broken-links`) | `slopstopper profile show`. Is that workflow listed as dropped, or is it genuinely failing? | The profile is right but too coarse for this one check | Add the workflow to `workflows.enabled` in `.slopstopper.yml` and re-run `install.sh` to install it, or triage it normally if it's already installed. A profile only ever subtracts; `enabled` is the per-check escape hatch | config |
| `reliability:api-health` or `security:api-headers` reports "Nothing to audit, so skipping" and exits 0 | `slopstopper config get api.health.path` / `api.headers.paths` | Neither key is set. Both API checks ship inert, the same contract as `headers.source: null`. This is the unconfigured state, **not** a pass | Set `api.health.path` (e.g. `/health`) and `api.headers.paths` in `.slopstopper.yml`. `slopstopper-install` Step 4 has the full block. If the repo has no API, the skip is the correct end state, or drop to `profile: library` | config |
| `reliability:api-health` fails on `field \`status\` is \`degraded\`, expected \`ok\`` while the endpoint returns HTTP 200 | `curl -s <url>/health` and read the body | Working as designed, and the reason this check isn't just a reachability probe: the service is telling you it's unhealthy. Not a check problem | Fix the dependency the body names (`deps.*` fields usually point at it). Only touch `api.health.expect_fields` if the *contract* changed deliberately, never to make a degraded service look healthy | code |
| `security:api-headers` fails on a wildcard `Access-Control-Allow-Origin` and the API is deliberately public | Read the finding: does it mention `Access-Control-Allow-Credentials`? | Two different findings. A **bare** wildcard on a public read-only API is fine. A wildcard **with credentials** never is. Browsers reject the pair, so the policy you intended was never being enforced | Bare wildcard → `api.headers.allow_wildcard_cors: true`. With credentials → fix the server to validate `Origin` against an allowlist and echo the match; the knob deliberately won't silence it | config OR code |
| `security:api-headers` fails on HSTS or `nosniff` but the headers are set at the CDN | Probe the deployed origin, not localhost: `task ss:security:api-headers -- https://api.example.com` | The edge adds them; a local process doesn't. A localhost run is auditing the wrong thing | Run the check against a deployed/preview URL (that's what CI does). If a header is genuinely handled by infrastructure the check can't see, `require_hsts` / `require_nosniff: false` with a `# why` comment | config |
| `security:api-headers` fails on an origin in `allowed_origins` that answers `(none)` | `curl -sI -H 'Origin: <that origin>' <url>` | The allowlist stopped matching, from a renamed frontend domain or a regex that no longer fires. This is the check's main job | Fix the server's allowlist, or remove the origin from `api.headers.allowed_origins` if it's genuinely retired | code |
| `reliability:api-latency` or `hygiene:openapi` reports "Nothing to sample/audit, so skipping" and exits 0 | `slopstopper config get api.latency.paths` / `api.openapi.spec` | Neither key is set. Both ship inert, the same contract as the other API checks. This is the unconfigured state, **not** a pass | Set `api.latency.paths` (the endpoints whose response time you care about) and `api.openapi.spec`. `slopstopper-install` Step 4 has the full block | config |
| `hygiene:openapi` skips with "this check reads JSON only" | Look at the `api.openapi.spec` value. Does it end `.yaml` / `.yml`? | Working as designed. `slopstopper-cli` has no YAML parser, so this check skips | Point `api.openapi.spec` at the JSON form, which most frameworks serve at `/openapi.json`. If the repo only has YAML, this check stays skipped and that is a real coverage gap worth naming, not a config error | config |
| `reliability:api-latency` fails a median budget in CI but passes locally | Compare the report's median against the budget, then re-run in the same environment | Almost always the environment, not the code: a cold-started preview deploy is slower and noisier than a warm local process. Budgets gate on the median precisely so one outlier doesn't do this, so a *median* breach means it was consistently slow | If the budget was guessed rather than observed, it's the budget that's wrong, so raise `api.latency.median_ms` to something derived from the reports, or unset it on PRs and rely on the scheduled production run. Only chase the code once the numbers say production regressed | threshold |
| `reliability:api-latency` fails with no budgets configured at all | Read the issue text. It will say "not reachable" or "answered HTTP N" | Not a budget failure. Reachability is the floor and is never opt-in: a timing taken from a connection error or a 500 isn't a measurement | Fix the endpoint or the URL. There is deliberately no knob to make an unreachable endpoint pass | code |
| `hygiene:openapi` reports an operation "served but missing from the committed spec" | `curl -s <served_spec_url>` and diff its `paths` against the committed file | The real thing this check exists for: someone shipped a route and didn't regenerate the spec. Not a false positive | Regenerate the spec from the running app and commit it. If the spec is generated at build time, point `api.openapi.spec` at the served URL instead so it can't drift at all | code |
| `hygiene:openapi` fails on a documented path that 404s, and the route is deliberately undeployed in this environment | `curl -i <url><path>` against the audited environment | Environment-specific routing, not drift, e.g. an admin route only deployed to production being probed on a preview URL | Add the path to `api.openapi.ignore_paths` (globs work) with a `# why` comment. Don't set `probe_paths: false` for one path, because that disables the whole reachability half | config |
| A check is red in the Actions tab but its PR comment says `✅ …: passed` (or there's no comment) | Compare the emit line in that workflow: `slopstopper emit <check> --target pr-comment --status ${{ steps.<id>.outcome … }}`. Does `<id>` name the step that actually decides the verdict? | The `--status` expression points at the wrong step. Every check fails its own step (exit 1 on findings, 2 when it couldn't run), except `hygiene:docs-size`, which is advisory (always exits 0) | Fix the expression in that workflow to read the deciding step's `outcome` (or the gate's output). The verdict is never inferred from report text. docs-size's report says ❌ while its step is green, so reading the text would get it wrong | config (workflow) |
| The PR summary comment is missing, stale, or omits a check | Was `ss-pr-summary.yml` triggered? Check the Actions tab for "SlopStopper · PR Summary" runs on that PR | `workflow_run` can't glob: a check workflow whose `name:` isn't in `ss-pr-summary.yml`'s `workflow_run.workflows` list never re-renders the summary. `workflow_run` also only fires for workflows that exist on the **default branch**, so a brand-new check workflow won't trigger it until merged | Add the workflow's exact `name:` to that list. For a not-yet-merged workflow, expect the summary to lag until the branch lands, which is a GitHub constraint, not a bug | config (workflow) |
| The summary says `⏳ N of M still running` and never settles | Re-read it after the last check finishes; each completion re-renders it | Working as designed. The summary is rendered from run conclusions, so a mid-flight suite honestly reports as unfinished rather than green | Nothing to fix. If it stays stuck with all checks complete, the last summary run failed, so check its logs | none |
| `task ss:hygiene:csp-exceptions` reports "no headers.source configured" with exit 0 | `cat .slopstopper.yml \| grep -A2 headers:` | `.slopstopper.yml` `headers.source` is null (the seeded default) | If you want the check active, set `headers.source` to your headers file (e.g. `public/_headers`) and `headers.format` to match (`cloudflare-text` for `_headers` files, `json` for JSON arrays, `meta` with `source` at the built HTML root when the CSP is a `<meta>` tag, `auto` to infer). Otherwise this is harmless. A `meta` source that isn't built skips locally and exits 2 in CI; build the site first | config |
| `slopstopper run hygiene:csp-exceptions` reports "Unknown headers.format" | Run `python3 -c "from slopstopper import headers_adapters; print(list(headers_adapters.ADAPTERS.keys()))"` | `.slopstopper.yml` `headers.format` doesn't match a shipped adapter | Set `headers.format` to one of the listed adapter names or `auto`. If you need a format slopstopper doesn't ship, add a module under `cli/slopstopper/headers_adapters/` and register it in `__init__.py`'s `ADAPTERS`. | config (or new adapter) |
| `task ss:hygiene:entry-files` fails with a file over its token budget | Run the task. It prints tokens per file and the cold-start cost (`AGENTS.md` always loaded + the map as the fallback hop) | `AGENTS.md` past ~2,000 estimated tokens (chars/4) is where agents start dropping rules; `README.md` past 600 (badges excluded) is carrying docs, not orientation; the map past 1,000 is an expensive hop | Move the content that serves the fewest tasks into a `docs/` topic doc and route it with a trigger-first "read" line; keep the one-line rules inline. Never raise the budget to pass | code (docs) |
| `task ss:hygiene:entry-files` fails with `missing_map_pointer` on README.md or AGENTS.md | Read `.ss/reports/entry-files/entry-file-size-report.md`, whose "How to fix" section emits the paste-ready line | `README.md` doesn't link `docs/README.md`, or `AGENTS.md` has no *explicit* route to it, because a "see docs/README.md" is a soft link and does not count (`require_explicit_routes`) | Paste the catch-all route as the last row of `AGENTS.md`'s routes (`For any task not covered above, read docs/README.md for …`) and a plain link into `README.md`. Confirm with `task ss:hygiene:entry-files`. If the rule genuinely doesn't fit this repo, set `hygiene.entry_files.require_map_pointer: false` with a `# why` comment | code (docs) OR tune |
| `task ss:hygiene:entry-files` fails with `claude_not_pure_include` on CLAUDE.md | `cat CLAUDE.md` | `CLAUDE.md` is anything other than exactly `@AGENTS.md`, such as a pointer paragraph, a heading or real rules. Claude Code expands the include, so any other content is a second copy that drifts | Replace the file contents with the single line `@AGENTS.md`; move anything real into `AGENTS.md`. `hygiene.entry_files.require_claude_include: false` accepts any content, for a repo that cannot use the include | code (docs) OR tune |
| `task ss:hygiene:entry-files` fails with `docs/README.md not found` | `ls docs/README.md docs/index.md` | The map is enforced but doesn't exist. A `docs/index.md` is the pre-0.15 map, and the report's fix section carries the rename; otherwise the install ran on a repo that already had `README.md`/`AGENTS.md` (which suppresses the scaffold) but no `docs/` | `git mv docs/index.md docs/README.md` and rewrite its rows as "When you are… \| Read …" routes, or write the map skeleton the report ships. Or disable: `hygiene.entry_files.require_map_pointer: false` AND `workflows.disabled` the docs-* workflows | code (docs) OR tune |
| `task ss:hygiene:entry-files` fails with `AGENTS.md has soft routes` | Read the report. It lists each `.md` link that names no trigger and no "read" as `AGENTS.md line N → <doc>: "…"` | Agents treat "see docs/x.md" as optional and skip it (measured: an unrouted runbook skipped one run in three); the check insists every `.md` link in `AGENTS.md` says when to read it | Reword each listed line as trigger → "read" → file → what it holds, or drop the link. A "When you are… \| Do this" table counts its header as the trigger for every row | code (docs) |
| `git push` is blocked by a slopstopper pre-push hook (output mentions `ss:hygiene:test`) | Re-run the exact gate, `task ss:hygiene:test` (or `mise exec -- task ss:hygiene:test`), the same command the hook runs | A hygiene check is genuinely red; the pre-push hook (`.githooks/pre-push`, wired via `core.hooksPath`) runs the static hygiene subset before every push | Fix the failing hygiene check via its row above, then push. To bypass a single push, `git push --no-verify`. To remove the gate entirely, unset `git config --unset core.hooksPath` (or reinstall with `--no-hooks`) | code (per failing check) |
| A slopstopper pre-push hook prints `mise/task not found, skipping` (or doesn't run at all) | `command -v mise; git config --get core.hooksPath` | mise isn't activated in the shell git spawned the hook from, or `core.hooksPath` was never wired | Activate mise (https://mise.jdx.dev/getting-started.html); confirm `core.hooksPath` is `.githooks` (`git config core.hooksPath .githooks` if missing). The hook goes through `mise exec` on purpose, because git hooks don't source your profile | config (environment) |
| A browser check (smoke, E2E, accessibility, broken links) fails on "Install Playwright browsers" with `Playwright browser install failed twice` | Open the step log: two `attempt N failed or stalled` warnings, no test output | The Chromium download stalled or failed on that runner twice in a row. ### Baseline security headers (for the missing-headers row above)

For a static site using GTM:

```
/*
  X-Content-Type-Options: nosniff
  X-Frame-Options: DENY
  Referrer-Policy: strict-origin-when-cross-origin
  Permissions-Policy: geolocation=(), camera=(), microphone=(), interest-cohort=()
  Cross-Origin-Opener-Policy: same-origin
  Cross-Origin-Resource-Policy: same-origin
  Content-Security-Policy: default-src 'self'; script-src 'self' 'unsafe-inline' https://www.googletagmanager.com https://*.googletagmanager.com; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:; connect-src 'self' https://*.google-analytics.com https://*.googletagmanager.com; font-src 'self' data:; base-uri 'self'; form-action 'self'; frame-ancestors 'none'
```

Tune `script-src` / `connect-src` to the actual third parties the site loads. `'unsafe-inline'` for `script-src` is the pragmatic call when the build tool injects inline scripts (Astro `define:vars`, GTM bootstrap) and you can't easily add nonces; tighten to nonces or hashes if the framework supports them. Any `'unsafe-inline'` retention should be documented in `docs/security/CSP_EXCEPTIONS.md` under `### /*` so the drift check and the next reviewer both see it.
